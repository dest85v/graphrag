# Feature Specification: Поддержка русского языка с вкраплениями англоязычных терминов

**Feature Branch**: `[005-ru-language-support]`  
**Created**: 2026-04-17  
**Status**: Draft  
**Input**: User description: "Надо реализовать задачу 'P1 — Добавить поддержку русского языка с вкраплениями англоязычных терминов'"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Индексация русскоязычных документов (Priority: P1)

Аналитики и исследователи в русскоязычных компаниях загружают внутренние документы на русском языке (отчёты, регламенты, технические спецификации) в GraphRAG для построения графа знаний. Сейчас эти документы обрабатываются некорректно: spaCy-модель `en_core_web_md` не распознаёт русские именные фразы, а RegexExtractor отсекает все кириллические слова как «невалидные токены». В результате граф знаний либо пуст, либо содержит только английские термины из русского текста.

**Why this priority**: Без этой возможности проект бесполезен для значительной части русскоязычных пользователей. Это фундаментальный барьер для выхода на русскоязычный рынок.

**Independent Test**: Можно полностью проверить, запустив пайплайн индексации на наборе из 50+ русских документов (документы, статьи, регламенты) и убедившись, что: (1) noun phrases извлекаются для кириллического текста, (2) сущности и отношения обнаруживаются LLM-экстрактором, (3) итоговый граф содержит релевантные сущности на русском языке.

**Acceptance Scenarios**:

1. **Given** пользователь загрузил русскоязычный документ в GraphRAG и настроил `nlp_model: "ru_core_news_md"`, **When** запускается индексация с `graphrag_nlp` стратегией, **When** извлекаются noun phrases через NLP-экстрактор, **Then** извлекаются корректные именные фразы на русском языке (например, «внутренний аудит», «финансовый отчёт», «руководство пользователя»).
2. **Given** русскоязычный документ проиндексирован, **When** запускается LLM-экстрактор графа с `language: "русский"`, **When** анализируются результаты, **Then** обнаруживаются сущности с русскими описаниями и отношения между ними.
3. **Given** документ на русском языке, **When** запускается entity summarization, **Then** итоговые описания сущностей генерируются на русском языке.

### User Story 2 — Смешанный RU+EN текст (Priority: P1)

Технические специалисты обрабатывают документы, содержащие русский текст с английскими терминами (типа "API endpoint", "deployment pipeline", "microservice architecture", "CI/CD"). Эти документы типичны для IT-компаний, где техническая документация пишется на русском, но профессиональная лексика остаётся на английском. Текущая реализация отбрасывает все не-ASCII символы через regex `^[a-zA-Z0-9\-]+$`, что означает потерю 100% кириллического текста и всех смешанных фраз.

**Why this priority**: Это самый частый сценарий в реальных корпоративных данных. Пренебрежение смешанным текстом означает, что основная масса технической документации будет обрабатываться неправильно.

**Independent Test**: Протестировать на наборе текстов, содержащих смесь русского и английского: запустить NLP-экстрактор и убедиться, что извлекаются и русские, и английские именные фразы, а также фразы, где английский термин встроен в русскую конструкцию (например, "настройка API", "логика deployment pipeline").

**Acceptance Scenarios**:

1. **Given** текст содержит смесь русского и английского («Настройка API сервера требует deployment pipeline»), **When** RegexExtractor или SyntacticParsingExtractor обрабатывает текст с Unicode-режимом валидации токенов, **Then** извлекаются noun phrases: «НАСТРОЙКА API СЕРВЕРА», «DEPLOYMENT PIPELINE» (или эквивалентные).
2. **Given** техническая документация с английскими терминами в русском контексте, **When** LLM-экстрактор обрабатывает chunk-и, **Then** англоязычные термины распознаются как сущности (например, «API» как инструмент, «deployment» как процесс).
3. **Given** смешанный текст, **When** entity summarization генерирует описания на русском, **Then** английские термины сохраняются в описаниях без потери смысла.

### User Story 3 — Выбор NLP-модели под язык документа (Priority: P2)

Компании, работающие с документами на нескольких языках, хотят гибко настраивать NLP-пайплайн. Для русскоязычных документов подходит `ru_core_news_md`, для мультиязычных корпусов — `xx_ent_wiki_sm`, для английских — `en_core_web_md`. Пользователь должен иметь возможность выбрать модель в конфигурации без изменения кода.

**Why this priority**: Гибкость выбора модели снижает затраты на инфраструктуру (меньше моделей — меньше RAM/диск) и повышает качество извлечения под конкретный языковой домен.

**Independent Test**: На одном наборе текстов на трёх языках протестировать три конфигурации модели и убедиться, что каждая модель корректно обрабатывает свой домен без ошибок.

**Acceptance Scenarios**:

1. **Given** пользователь указал в конфиге `nlp_model: "xx_ent_wiki_sm"`, **When** GraphRAG инициализирует NLP-пайплайн, **When** обрабатываются тексты на русском, английском и немецком, **Then** все три языка обрабатываются корректно одной моделью.
2. **Given** пользователь указал `nlp_model: "ru_core_news_md"`, **When** обрабатывается чисто русский текст, **Then** качество извлечения сущностей не ниже, чем с `xx_ent_wiki_sm` для русского языка.
3. **Given** указана несуществующая модель, **When** GraphRAG пытается загрузить модель, **Then** система пытается автоматически скачать её (через `spacy.cli.download`) и выдаёт понятную ошибку, если скачивание невозможно.

---

### Edge Cases

- Текст на одном языке, но с заимствованными терминами другого языка (например, русский текст с терминами из французского или японского).
- Текст с цифрами и спецсимволами (версии, IP-адреса, URL) в кириллическом контексте.
- Очень короткие тексты (1-3 слова) на русском — должна ли система извлекать noun phrases или допускать пустой результат.
- Текст, содержащий только английские слова внутри кириллического контекста (например, «Читай API документацию»).
- Документ, где один параграф на русском, другой на английском — как NLP-экстрактор обрабатывает такие переходы.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST извлекать именные фразы из кириллического текста (русского языка) с использованием настраиваемой spaCy-модели.
- **FR-002**: Система MUST корректно обрабатывать валидацию токенов, содержащих не-ASCII символы (кириллицу, латиницу, цифры, дефисы), через Unicode-aware regex-паттерн.
- **FR-003**: Система MUST поддерживать настраиваемую NLP-модель через конфигурационное поле `nlp_model`, с выбором из предустановленных вариантов (`en_core_web_md`, `ru_core_news_md`, `xx_ent_wiki_sm`) или произвольного названия.
- **FR-004**: Система MUST автоматически загружать указанную spaCy-модель при первом использовании (с автоскачиванием через `spacy.cli.download`, если модель отсутствует).
- **FR-005**: Система MUST извлекать именные фразы из смешанного RU+EN текста, включая английские термины, встроенные в русскую синтаксическую конструкцию, и наоборот.
- **FR-006**: Система MUST сохранять обратную совместимость: поведение по умолчанию (en_core_web_md, ASCII-only валидация) не должно меняться для существующих пользователей без явного указания новой конфигурации.
- **FR-007**: Система MUST обеспечивать LLM-экстрактор и summarization корректную обработку русского текста через существующий механизм `{language}` placeholder.
- **FR-008**: Система MUST предоставлять опциональные зависимости для установки русскоязычных spaCy-моделей через extras (`[nlp-ru]`, `[nlp-xx]`).

### Key Entities

- **NLP-экстрактор**: Компонент (RegexExtractor, SyntacticParsingExtractor, CFGExtractor), извлекающий именные фразы из текста. Ключевые атрибуты: `nlp_model` (название spaCy-модели), `max_word_length`, `exclude_nouns`. В текущей реализации привязан к английскому языку.
- **NLP-модель**: spaCy-модель для анализа текста. В текущей реализации используется только `en_core_web_md`. Требуется поддержка `ru_core_news_md` (моноязычная русская) и `xx_ent_wiki_sm` (мультиязычная NER).
- **Именная фраза (Noun Phrase)**: Извлечённая фраза — однословная с proper noun или многословная. Представляется как строка в верхнем регистре. Ключевые свойства: наличие proper nouns, наличие compound-слов, валидность токенов.
- **Валидация токена**: Проверка, является ли слово допустимым для включения в noun phrase. В текущей реализации — ASCII-only regex, блокирующий все не-латинские символы.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: RegexExtractor извлекает noun phrases из кириллического текста — не менее 90% тестовых именных фраз из набора из 50+ русских документов обнаруживаются (по метрике recall).
- **SC-002**: На смешанном RU+EN тексте (100+ примеров) извлекаются корректно как русские, так и англоязычные именные фразы — recall >= 85% для обоих языков.
- **SC-003**: Пользователь может переключить NLP-модель на `ru_core_news_md` или `xx_ent_wiki_sm` через конфигурацию без изменений в коде — пайплайн индексации завершается без ошибок.
- **SC-004**: Опциональные зависимости `[nlp-ru]` и `[nlp-xx]` позволяют установить русскоязычные spaCy-модели одной командой (`uv add graphrag[nlp-ru]`).
- **SC-005**: Существующий функционал на английском языке не нарушается при добавлении Unicode-поддержки — Jaccard similarity между old (ASCII-only) и new (Unicode) RegexExtractor на английских текстах >= 95%.

## Assumptions

- spaCy уже является зависимостью проекта (`spacy~=3.8`), русскоязычные модели (`ru_core_news_md`, `xx_ent_wiki_sm`) доступны через `spacy download`.
- Токенизатор `o200k_base` (по умолчанию в GraphRAG) поддерживает кириллицу и мультиязычные тексты — дополнительная конфигурация не требуется.
- LLM-экстрактор и summarization работают на основе `{language}` placeholder и уже поддерживают русский язык через `prompt_tune` language detection.
- Token-based chunking не зависит от языка — токенизация через `o200k_base` корректно разделяет кириллические и латинские тексты на chunks.
- Конфигурационное поле `nlp_model` будет добавлено в существующую модель `ExtractGraphNlpConfig` без изменения API для downstream-кода.
- Обратная совместимость: по умолчанию остаётся `en_core_web_md` с ASCII-only валидацией — новые пользователи могут переключиться явно.
